# OpenVaultDB MVP — Implementation Journal

Started: 2026-07-09

## Goal

Prove: `sneat-cli → Sneat facades → DALgo → dalgo2openvaultdb → OpenVaultDB API (ovdb serve) → SQLite | inGitDB`
without changing Sneat business logic.

## Decisions

- 2026-07-09 (user steer): `dalgo2openvaultdb` lives under the **dal-go** org as a public repo —
  module `github.com/dal-go/dalgo2openvaultdb`, local path `~/projects/dal-go/dalgo2openvaultdb`.
  Will be created/published on GitHub under dal-go once initial content exists.
  The prompt's `~/projects/openvaultdb-org/dalgo2openvaultdb` path is superseded by this steer.
- Delegation policy (user steer): research and well-specified implementation on cheaper models
  (sonnet), top model reserved for design/integration.
- **Engine contract is an internal interface, not dal.DB.** Engines expose
  Get/Exists/Scan/Apply(batch)/EnsureCollection over `map[string]any` documents. Core resolves
  DALgo update ops (nested field paths, DeleteField, increment) itself via read-modify-write
  under a per-database write mutex, because dalgo2ingitdb only supports single-segment update
  paths while Sneat facades need nested `ByFieldPath` + `DeleteField`. Uniform semantics across
  engines; engines stay tiny.
- **Queries are filtered in core, not in engines.** Engines only `Scan(collection)`; core applies
  where/order/limit. MVP-scale trade-off, documented; pushes filter pushdown to roadmap.
- **SQLite store is hand-rolled** (table per collection: `id TEXT PRIMARY KEY, data TEXT` JSON),
  `modernc.org/sqlite` (pure Go). Existing `dal-go/dalgo2sqlite` is relational
  (columns per field via dalgo2sql) — wrong shape for nested Sneat DTOs; noted as the future
  per-column engine option.
- **inGitDB engine reuses `github.com/ingitdb/dalgo2ingitdb v0.1.x`** (per research: works on a
  plain dir, git commit opt-in via TxWithMessage, definition.yaml required per collection).
  Schemaless mode = auto-create collection `definition.yaml` on first write from observed fields
  (all optional) via the driver's DDL interface; inferred catalogue keeps observing after that.
- **Sneat e2e seam**: `facade.GetSneatDB` package var. sneat-cli `convo` sandbox
  (`convodev.SetupSandbox` in sneat-bots) currently hardcodes dalgo2memory; add
  `SetupSandboxWithDB(db dal.DB, ...)` (dev helper, not business logic) and select the driver in
  sneat-cli via `SNEAT_STORAGE=openvaultdb` + `OPENVAULTDB_URL`, mirroring sneat-go's
  `sneatstorage` ingitdb override pattern.
- **Driver transactions**: buffered ordered write ops → single `POST /batch` on commit
  (server applies in one engine tx = one git commit for inGitDB). Reads pass through;
  staged sets/inserts are served back to reads within the tx (best-effort read-your-writes).
- Sneat e2e validation runs on inGitDB (schemaless — no need to declare Sneat's deep DTO
  schemas); SQLite strict is proven by conformance/unit tests with declared test schemas.
  Sneat-on-SQLite-strict would require full Sneat schema declarations — follow-up.
- Conformance: `end2end.TestDalgoDB` test lives in the openvaultdb repo (spins in-process
  httptest server + driver), so the published dalgo2openvaultdb module depends only on dalgo.

## The dalgo-native pivot (user steer, mid-build)

The first cut had a custom `engine.Engine` interface with adapters. Alex redirected:
ovdb must use **dalgo itself** internally — engines are dal.DB drivers; ovdb only
authenticates/validates and passes through (DTQL as the eventual query surface).
Rebuilt `pkg/core` accordingly; deleted `pkg/engine` (custom Key type also replaced
with `*dal.Key` after a second nudge). Query evaluation, update application, and
storage all happen in the drivers now. dalgo's `dtql` package turned out to exist
and `dtql.Deserialize` made the `/dtql` endpoint nearly free.

## Upstream work done instead of workarounds ("do not reinvent inGitDB driver!")

- dalgo2ingitdb (local clone, uncommitted): subcollection DDL (path-form
  CreateCollection names), ErrRecordAlreadyExists sentinel, idempotent Delete +
  empty query results for unknown collections, nested field-path updates
  (delete-field/increment/server-timestamp), git staging fixed to absolute
  pathspecs (commits from a server running outside the repo dir failed before).
- dalgo2sqlite (local clone, uncommitted): mattn/go-sqlite3 (cgo) → modernc.org/sqlite
  (their README's open question; also unblocks this cgo-less environment).
- dalgo2sql (local clone, uncommitted): map[string]any Get/GetMulti/Set support,
  key-wrapping not-found errors, rows-leak deadlock fix in existsSingle,
  readers return dal.ErrNoMoreRecords.
- sneat-bots (uncommitted): convodev.SetupSandboxWithDB(db, ...) — injectable
  sandbox DB with idempotent seeding (persistent stores keep the space between runs).
- sneat-cli (uncommitted): SNEAT_STORAGE=openvaultdb + OPENVAULTDB_URL/OPENVAULTDB_DB
  select dalgo2openvaultdb for convo sandbox; local replaces for sneat-bots + driver.

## Findings the conformance suite caught

- Contract doc error: dal Get must RETURN the not-found error (memory driver does),
  not just SetError — fixed driver + doc.
- dal.NewRecordWithData wants the bare map, not &map (reference semantics).
- Sneat's space-module records use nested keys (spaces/{id}/ext/{module}) → needed
  subcollection DDL + parent-scoped queries (calendarius GetActiveSingleHappenings
  was the one that failed silently — empty calendar while memory backend showed the
  event; fixed by adding "parent" to the wire query).
- Keys-only queries have an implicit sorted-by-ID contract (limit after sort);
  SQL drivers return insertion order → core sorts keys-only-without-order results.
- SQLite type drift: booleans come back 0/1 → schema-driven coercion on reads;
  "id" PK column is implicitly declared for validation.

## Trade-offs / Deviations

- Sneat e2e runs on inGitDB schemaless; Sneat-on-SQLite-strict would need full DTO
  schema declarations (roadmap).
- Strict/partial validation is a pre-flight SIMULATION (batch staged against store
  state before any write) because inGitDB cannot roll back written files. Simulation
  and driver update semantics could theoretically drift — documented.
- dalgo2sql readers don't set record keys (PK returns in the "id" column) → ovdb
  rebuilds keys from it; proper fix is upstream (roadmap).
- ovdb default-generates git commit messages ("ovdb: insert×2 in spaces, ext") when
  the client sends none — otherwise Sneat facades produce no history.
- inGitDB push policy (user request): manifest storage.ingitdb.push none|sync|async;
  sync verified against a local bare remote; async = coalescing single-flight pusher.
  Deliberate save/commit/push model captured as an idea doc:
  ingitdb/spec/ideas/transactions-save-commit-push-model.md (user request).
- sneat-cli has 6 pre-existing errcheck lint findings (convo.go prints, not this diff).
