## Confirmed finding

### ACL24-R1 — medium — introduced: real owner denials lose structured authorization at the CLI boundary

Location: datatug-cli/pkg/openvaultdb/client.go, ValidateAuthorizationEnvelope, approximately lines 159–171; pkg/openvaultdb/source.go, ExecuteQueryToRecordsReader, forbidden/unauthorized response branch. Provider counterpart: openvaultdb-go/pkg/server/httperr.go, errorBody/errorDetail, approximately lines 14–22, and pkg/server/access.go, writeQueryAuthorizationError.

Concrete trigger: execute a DTQL projection rejected by a real OpenVaultDB owner policy through the DataTug OpenVaultDB source. OpenVaultDB serializes the decision inside error.authorization. The CLI's ValidateAuthorizationEnvelope reads only envelope["authorization"]. Its forbidden-response branch therefore receives a decode failure and returns bare access.ErrAccessDenied instead of AuthorizationError. exec_run_query only emits details.authorization when errors.As finds AuthorizationError, so the current browser loses all owner blocker/layer details on this real path.

This remains fail-closed for data; the defect is loss of the newly promised diagnostics and actual provider/consumer contract mismatch. The endpoint mock uses a top-level authorization field and therefore passes against a response shape the real server does not emit. The real-server secureread test checks errors.Is(..., access.ErrAccessDenied), which passes even after the decision is discarded.

Recommended action: decode the real nested error envelope separately from successful top-level UPDATE envelopes; retain strict duplicate-key and authorization validation. Correct the mock. Extend the actual SQLite/InGitDB server regression to assert errors.As to AuthorizationError and preserved owner decisions, then verify details.authorization at the endpoint boundary. Parent has acknowledged this finding and is implementing ordinary regression coverage. No remediation was reviewed here.

## Unvalidated security concern requiring follow-up

### ACL24-C1 — potentially high — introduced protected SQLite path: incoming foreign-key side effects are not excluded by the inspected schema gate

Location: dalgo2sql/sqlite_protected.go, prepare, approximately lines 239–270 (trigger and foreign_key_list checks), and execute, approximately lines 458–461 (DELETE).

Static evidence: preparation checks triggers attached to the target table and PRAGMA foreign_key_list(target). That pragma describes the target table's outgoing references. It does not enumerate other tables referencing the target. The newly introduced protected execution supports DELETE and executes it after assessing the explicit target. An incoming referential action may affect another table that is absent from the explicit operation's candidate/evidence and owner decisions.

The source inspected does not establish that foreign-key enforcement is disabled on every caller-supplied connection. NewDatabase accepts a caller-supplied sql.DB. The existing negative fixture covers a target with an outgoing foreign key, not a referenced parent with incoming actions.

Recommended action: investigate incoming references in the same storage transaction and reject schemas capable of unassessed side effects under this bounded profile, or demonstrate an existing reliable invariant that prevents them. Do not broaden ACL functionality as part of a fix. Add normal regression coverage for the supported/rejected schema boundary.

Confidence/limit: this is a static concern, not a validated exploit or executed reproduction. The review was interrupted before experimental validation, and the parent expressly instructed me not to continue security reproductions. I do not claim an observed unauthorized mutation. It is not counted as a confirmed high-severity finding.
